# 一、先建立正確的效能模型

SwiftUI 的效能問題,99% 是「**body 被重算的次數太多 / 範圍太大**」,而不是「畫面繪製太慢」。所以優化的核心只有一句:

> **讓「依賴某狀態的 body」盡量小、盡量少。**

要做到這件事,得先精準理解「一次狀態改變,到底有哪些 body 會重算」。它由三個機制共同決定:

1. **依賴追蹤**:哪些 View 的 body「讀過」這個狀態。
2. **值比較**:被重建的子 View,輸入有沒有變(沒變就跳過 body)。
3. **identity**:這次的 View 和上次是不是「同一個」(換 id = 整個重建)。

下面逐一拆開,每一條都對應一種優化手段。

---

# 二、機制一:依賴追蹤 —— 只有「讀過」才會被通知

SwiftUI 在執行 `body` 時,記錄「這個 body 讀取了哪些狀態」。之後**只有那些狀態變動,才會讓這個 body 重算**。

```swift
struct Row: View {
    @Environment(CartModel.self) private var cart
    let index: Int
    var body: some View {
        Text(cart.items[index].name)   // 只讀了 items → coupon 變動不會重算這列
    }
}
```

## 關鍵:`@Observable` 是「屬性級」追蹤

這是 `@Observable`(iOS 17+)勝過舊 `ObservableObject` 的核心。

- **舊 `ObservableObject`**:任何一個 `@Published` 變動 → **所有觀察這個物件的 View 都收到通知**,即使它根本沒用到那個屬性。
- **新 `@Observable`**:只通知「**body 實際讀到那個屬性**」的 View。

```swift
@Observable class Model { var a = 0; var b = 0 }

// 只讀 a 的 View:b 改變時「完全不會」重算 → 這是 @Observable 自動做到的
Text("\(model.a)")
```

> 實務啟示:把大物件拆成「按變動頻率分群」的小 `@Observable`,或讓每個 View 只讀它真正需要的屬性,重繪範圍就自然縮小。詳見 [[Observable 與 ObservableObject 對比]]。

## 陷阱:在父層「讀」了狀態,等於把依賴擴散到整個父 body

```swift
var body: some View {
    let name = cart.items[0].name   // ❌ 在父 body 讀 → 父 body 依賴 items
    return VStack {
        Header()                     // 跟 name 無關,卻被連累一起重算
        Text(name)
    }
}
```

**把讀取下放到真正需要的子 View**,父層就不必依賴它:

```swift
var body: some View {
    VStack {
        Header()         // 不再被連累
        NameLabel()      // 讀取收在這裡
    }
}
```

# 三、機制二:值比較 —— 讓 SwiftUI 能「跳過」子 View

回顧 [[核心架構與機制#重建 struct ≠ 重算 body(常見誤解)|重建 ≠ 重算]]:父 body 重算時,子 View struct 會被重建,但若**輸入沒變**,SwiftUI 會跳過子 body。問題是 ——「沒變」怎麼判斷?

SwiftUI 對 View 的儲存屬性做比較。**當屬性都是可輕易比較的值(POD:Int、String、小 struct)時,跳過很可靠**;但下列情況會讓它「無法確定沒變」,於是保守地重算:

| 讓比較失效的東西 | 為什麼 | 對策 |
| --- | --- | --- |
| 閉包屬性 (`() -> Void`) | 閉包不可比較,每次都當成「不同」 | 盡量別把大量 callback 往下傳;或讓 View `Equatable` 只比真正的資料 |
| 引用型別 (class) 屬性 | 比的是「是不是同一個物件」,內容變了也可能比不出來 | 傳「值」而非整個物件;或拆小 |
| 把整個大物件往下傳 | 物件任一處變,整個子樹被當成變了 | 只傳子 View 真正需要的小欄位 |

## 工具:`Equatable` + `.equatable()`

當你**很清楚**某個子 View「只依賴某幾個值」,可以讓它遵循 `Equatable`,手動定義「什麼情況算相同」,SwiftUI 就用你的規則來跳過:

```swift
struct ExpensiveRow: View, Equatable {
    let item: Item
    static func == (l: Self, r: Self) -> Bool {
        l.item.id == r.item.id && l.item.name == r.item.name   // 只在乎這兩個
    }
    var body: some View { /* 昂貴內容 */ }
}

ExpensiveRow(item: item).equatable()   // 用上面的 == 來決定要不要重算
```

> 注意:`.equatable()` 不是免費的 —— 比較本身也有成本。**只在「body 昂貴 + 重算很頻繁 + 比較很便宜」時才值得**。多數情況靠「傳值、拆小」就夠了,不必動用它。

# 四、機制三:identity —— 別不小心整個重建

換掉一個 View 的 identity = 告訴 SwiftUI「這是全新的東西」→ 丟棄舊的、重建新的、**重置 `@State`**、播放轉場動畫。這比「重算 body」昂貴得多。

## 反模式 1:在 `ForEach` 用 index 當 id

見 [[列表與 ForEach Identity#四、用 index 當 id —— 經典陷阱|index 當 id 陷阱]]:重排/增刪會讓身份錯亂,導致大量本可重用的列被重建。**永遠用 `Identifiable` 的穩定 id。**

## 反模式 2:用 `AnyView` 抹除型別

```swift
var body: some View {
    if cond { return AnyView(A()) }
    else    { return AnyView(B()) }     // ❌ 型別被抹除
}
```

`AnyView` 讓 SwiftUI 失去「這兩次是不是同一種 View」的編譯期資訊,**diff 能力下降、無法有效重用**。改用 `@ViewBuilder`(`if/else` 直接寫在 body,型別由編譯器保留):

```swift
@ViewBuilder var body: some View {
    if cond { A() } else { B() }        // ✅ 型別保留,diff 正常
}
```

## 善用 identity:`.id()` 主動重置

反過來,當你**想要**「換資料時整個畫面狀態歸零」(例如換使用者重載表單),`.id(user.id)` 是正確工具 —— 這是有意識地利用 identity,而非誤用。

# 五、常見「無謂重繪」來源清單

按出現頻率排序,排查時從上往下看:

1. **把整包 `@Observable` 大物件往下傳**,子 View 只用其中一個欄位 → 物件任一處變就全重繪。**拆小 / 只傳欄位。**
2. **在父 body 讀取了高頻變動的狀態** → 整個父 body 跟著高頻重算。**把讀取下放。**
3. **`ForEach` 用 index / 不穩定 id** → 列被大量重建。**用穩定 id。**
4. **到處 `AnyView`** → diff 失效。**換 `@ViewBuilder` / `Group`。**
5. **`GeometryReader` 包太大範圍** → 它貪心撐滿且其內容易被牽動重算。**縮小範圍**(見 [[佈局系統 Layout#七、`GeometryReader` —— 取得實際可用空間|Layout]])。
6. **在 body 裡做昂貴運算**(排序、格式化、建 formatter)→ 每次重算都重跑。**移到 model / 快取 / `let` 常數。**
7. **每次都 new 一個物件當依賴**(該用 `@StateObject`/`@State` 卻用 `@ObservedObject` 建立)→ 見 [[Observable 與 ObservableObject 對比#⚠️ 經典 bug:該用 `@StateObject` 卻用了 `@ObservedObject`|經典 bug]]。

# 六、body 裡不該做的事

`body` 會被呼叫很多次,所以它必須**廉價且純**:

```swift
var body: some View {
    let formatter = DateFormatter()        // ❌ 每次重算都建一個(很貴)
    formatter.dateStyle = .long
    return Text(formatter.string(from: date))
}
```

改成「只建一次」:

```swift
private static let formatter: DateFormatter = {   // 靜態 → 全程只建一次
    let f = DateFormatter(); f.dateStyle = .long; return f
}()
var body: some View { Text(Self.formatter.string(from: date)) }
```

原則:**body 裡只做「組裝畫面」,不做「計算與副作用」**。昂貴計算放 model 並快取;副作用(網路、寫檔)放 `.task` / `.onChange`(見 [[生命週期與 task]])。

# 七、惰性容器與大量資料

- 長列表用**惰性**容器:`List` / `LazyVStack` / `LazyHStack` / `LazyVGrid` —— 只建可見的列(見 [[列表與 ForEach Identity#六、`List` vs `LazyVStack` vs `ForEach` 單用|List vs LazyVStack]])。
- `VStack { ForEach(huge) }` 會**一次建立全部**,資料一多就卡 —— 別用在長列表。
- 列內容若昂貴(圖片、複雜排版),搭配穩定 id 讓捲動時能重用,而不是反覆重建。

# 八、怎麼「看見」重繪(量測)

不要靠猜,要量測:

## 方法 1:印出 body 執行次數

最土但最有效 —— 在可疑 View 的 body 放一個副作用觀察點:

```swift
var body: some View {
    let _ = Self._printChanges()   // Apple 提供:印出「這次是什麼導致重算」
    return Text(item.name)
}
```

`_printChanges()` 會在 console 告訴你「**是哪個屬性 / 狀態的變化觸發了這次重算**」,定位無謂重繪非常好用。

## 方法 2:Instruments — SwiftUI template

Xcode 的 Instruments 有 **SwiftUI** 與 **Hangs / Time Profiler** 範本,可看到:

- 每個 View 的更新次數與耗時(View Body / View Properties)。
- 哪一幀掉幀、哪個 body 是熱點。

> 流程建議:**先用 `_printChanges()` 找出「誰被重算了不該被重算」,再用 Instruments 確認「它是不是真的貴」**。先定位、再量化,別過早優化。

# 九、優化心法總結

1. **效能 = body 重算的次數 × 範圍 × 單次成本** —— 三者都可以單獨下手。
2. **縮小依賴**:`@Observable` 屬性級追蹤、讀取下放、物件拆小、只傳欄位。
3. **幫 SwiftUI 跳過**:傳值而非物件、避免閉包/引用屬性破壞比較,必要時 `Equatable` + `.equatable()`。
4. **保護 identity**:穩定 id、避免 `AnyView`、有意識地用 `.id()`。
5. **body 保持純與廉價**:昂貴運算移出、formatter 只建一次。
6. **長列表用惰性容器。**
7. **先量測再優化**:`_printChanges()` + Instruments,不要憑感覺。
